# Knowledge Loop — Challenge Grid

Severity: **P0 Critical** · **P1 High** · **P2 Medium** · **P3 Low**
Type: **W** = Weakness · **G** = Gap (missing work) · **O** = Opportunity

---

## Rule Lifecycle

| #   | Area               | Issue                                                 | Description                                                                                                                                                                                                                                                                                        | Type | Severity |
| --- | ------------------ | ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---- | -------- |
| 1   | validate-knowledge | **INFERRED-WRITE auto-executes without human gate**   | The skill auto-writes to domain-rules.yaml when it infers intent is "unambiguous" from reading two PRDs. But LLM inference is not deterministic — a plausible-sounding but wrong inference silently corrupts the YAML. This is the only auto-path that writes permanent data.                      | W    | **P0**   |
| 2   | validate-knowledge | **Conflict check can be stale at ship time**          | validate-knowledge runs at /write-a-prd. Between PRD creation and /ship-feature, another PRD may ship and add rules to the YAML. The conflict check that passed at PRD time is now stale. The only re-check at ship time is for supersede actions — new `action: add` rules go in with no re-scan. | W    | **P1**   |
| 3   | validate-knowledge | **Cheap LLM misses subtle semantic overlap**          | The skill explicitly recommends the cheapest model (Haiku) for the text comparison scan to save cost. But subtle domain overlap — two rules that use different vocabulary but govern the same business decision — requires richer reasoning. The framework optimizes cost over correctness here.   | W    | **P1**   |
| 4   | domain-rules.yaml  | **plain_english length not enforced**                 | The schema says "minimum ~80 words." This is a comment, not a constraint. A short `plain_english` value like "1 point per dollar" passes silently and makes conflict detection unreliable. There is no guard that rejects a rule with insufficient description before it enters YAML.              | W    | **P1**   |
| 5   | domain-rules.yaml  | **depends_on graph has no validation**                | Rules can declare `depends_on` pointing to other rule IDs. Nothing checks that the referenced ID exists, is active, or that the graph is acyclic. A circular dependency (`RULE-A depends_on RULE-B depends_on RULE-A`) would be silently accepted and only cause confusion later.                  | G    | **P2**   |
| 6   | domain-rules.yaml  | **Supersede chains become unreadable**                | After several PRDs, a rule can have a chain: 1.1.1 → superseded_by 1.1.2 → superseded_by 1.1.3 → superseded_by 1.1.4. There is no "what is the current version of this concept?" lookup. A new agent has to follow the chain manually. The framework has no chain-summary view.                    | W    | **P2**   |
| 7   | rule IDs           | **PRD-embedded IDs become misleading after revision** | `RULE-BILLING-P10-1` tells you the rule originated in PRD #10. But if the rule is substantially revised in PRD #14, the ID still says P10. An agent reading the rule in a future ticket would fetch PRD #10 for context — which no longer matches the current state of the rule.                   | W    | **P3**   |

## AGENT_CONTEXT.md & Knowledge Documents

| #   | Area             | Issue                                                     | Description                                                                                                                                                                                                                                                                                                                                               | Type | Severity |
| --- | ---------------- | --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---- | -------- |
| 8   | AGENT_CONTEXT.md | **Parallel tickets writing to same file — git conflicts** | Two tickets running in parallel in the same domain both append to `## Ticket handoffs` before opening their PRs. If they run truly in parallel, the second commit will conflict with the first. The framework doesn't acknowledge this and has no merge strategy.                                                                                         | W    | **P1**   |
| 9   | AGENT_CONTEXT.md | **Stale references never audited**                        | After a major refactor, AGENT_CONTEXT.md may still reference deleted module names (`OrderCalculator`), old file paths, or deprecated patterns. The framework has no periodic scan of AGENT_CONTEXT.md for references that no longer exist in the codebase. YAML gets careful lifecycle tracking; the context file does not.                               | G    | **P1**   |
| 10  | AGENT_CONTEXT.md | **Handoff notes lost if conversation ends prematurely**   | The ticket window is supposed to append handoff notes before opening the PR. If the user closes the conversation, hits context limits, or the agent crashes mid-session, the handoff is never written. The next ticket window sees an incomplete or empty handoff section and has no signal that information is missing.                                  | W    | **P1**   |
| 11  | AGENT_CONTEXT.md | **Known debt never closes**                               | The Known debt section in AGENT_CONTEXT.md is append-only in practice. There is no mechanism for marking a debt item as resolved or for closing it at ship-feature when the debt is addressed. Over time, the section accumulates historical entries that have been resolved but still appear as open debt.                                               | G    | **P2**   |
| 12  | grill-me logs    | **No cross-PRD index or search interface**                | Grill-me logs are saved to `grill-me-docs/<name>/grill-me-NN.md`. The intent is that humans and Claude can search past sessions. But there is no index file, no tag system, and no search skill. A human doing an ad-hoc search has to grep a folder tree. As the number of PRDs grows, this becomes impractical.                                         | G    | **P2**   |
| 13  | archetypes       | **Archetype is a forced binary choice**                   | scaffold-domain asks you to pick one of four archetypes. A domain that is 70% backend logic and 30% external API integration must pick one. The chosen archetype determines which optional sections appear in the template. The other 30% either gets no section or gets added manually — which is fine but the archetype model doesn't acknowledge this. | W    | **P3**   |

## PRD & Ticket Management

| #   | Area               | Issue                                                  | Description                                                                                                                                                                                                                                                                                                                                                                                   | Type | Severity |
| --- | ------------------ | ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---- | -------- |
| 14  | write-a-prd        | **Two-step rule ID minting can fail silently**         | After `gh issue create` returns the issue number, the skill must edit the PRD body to replace ID placeholders. If that edit fails (network error, auth expiry, gh CLI bug), the rule IDs are minted in the agent's memory but never written to the PRD. The PRD has placeholder text; domain-rules.yaml and AGENT_CONTEXT.md have IDs that don't appear anywhere the human can see.           | W    | **P1**   |
| 15  | write-a-prd        | **No "out of scope" section in PRD template**          | The PRD template has Problem, Solution, User Stories, Implementation Decisions, Testing Decisions, Business Rules Affected. It has no explicit "Out of Scope" section. Scope creep is easy — an agent or user adds a user story that implicitly expands scope without a clear boundary being declared.                                                                                        | G    | **P2**   |
| 16  | write-a-prd        | **PRD template is additive only**                      | The template is designed for feature PRDs (adding new behavior). Refactor PRDs, migration PRDs, and deprecation PRDs have fundamentally different content — they remove or replace existing behavior. The template doesn't have "What is being removed," "Why the current approach is wrong," or "Migration path" sections. Writing a refactor PRD requires fighting the template.            | G    | **P1**   |
| 17  | grill-me           | **5-branch interview optimized for new features only** | The branches are: Scope & Problem, Use Cases, Workflow Actors, Dependencies, Domain Terms. These are right for feature PRDs. For a bug fix, the right questions are: reproduction steps, affected users, root cause hypothesis, regression risk. For a refactor: what is wrong with the current approach, migration path, rollback plan. The same interview script is used for all PRD types. | W    | **P1**   |
| 18  | grill-me           | **No validation that all 5 branches were completed**   | The grill-me skill asks the agent to cover all 5 branches. But there is no checklist enforcement. An agent could shortcut and declare grill-me complete after covering 3 branches. update-agent-context would accept the incomplete output with no warning.                                                                                                                                   | W    | **P2**   |
| 19  | break-into-tickets | **No ticket complexity estimate**                      | Tickets are defined by description and dependency. There is no estimate of complexity (hours, test coverage expected, number of modules touched). A ticket described as "one endpoint" might require 5 hours of unexpected migration work. The team has no signal until work starts.                                                                                                          | G    | **P2**   |
| 20  | break-into-tickets | **Dependency text gets stale on ticket splits**        | If Ticket 1 is later split into Ticket 1a and 1b, the dependency text "requires: Ticket 1 merged" in Tickets 2, 3, 4 becomes ambiguous — does it mean 1a merged, 1b merged, or both? There is no mechanism to propagate dependency updates through the task list.                                                                                                                             | W    | **P2**   |

## Ship / Deploy / Rollback

| #   | Area         | Issue                                          | Description                                                                                                                                                                                                                                                                                                                                                        | Type | Severity |
| --- | ------------ | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---- | -------- |
| 21  | ship-feature | **No partial shipping model**                  | ship-feature is "once per PRD, all tickets merged." If 7 of 8 tickets merge and the 8th is blocked indefinitely (external dependency, team decision to defer), there is no path to ship the 7 that are done and defer the 8th to a new PRD. The entire PRD stays open.                                                                                             | G    | **P1**   |
| 22  | ship-feature | **No rollback mechanism**                      | If a shipped PRD turns out to be wrong — the rule was incorrect, the code has a critical bug, the business decision was reversed — there is no skill or procedure for rolling back. Rules would need to be manually un-superseded, code reverted, AGENT_CONTEXT.md restored from git. The framework has no "undo a PRD" concept.                                   | G    | **P1**   |
| 23  | ship-feature | **Divergence check is a high-reasoning task**  | Step 1 of ship-feature asks the agent to compare "what the PRD described" with "what the code actually implements" and flag divergence. This requires the agent to read and fully understand both the PRD and all merged code. This is one of the most complex reasoning tasks in the framework and the most likely to produce a false "no divergence" conclusion. | W    | **P2**   |
| 24  | ship-feature | **Ticket handoff history permanently deleted** | `## Ticket handoffs` is cleared at ship-feature. If a post-ship bug requires understanding what interfaces Ticket 3 created or what design decision Ticket 5 made, that information is gone. Git history has the code, but not the reasoning. The grill-me log has the pre-implementation thinking, but not the in-flight decisions.                               | W    | **P2**   |

## Multi-Agent / Multi-Domain / Concurrency

| #   | Area           | Issue                                                    | Description                                                                                                                                                                                                                                                                                                                                                                                | Type | Severity |
| --- | -------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---- | -------- |
| 25  | process        | **Multiple concurrent PRDs in same domain not modelled** | The framework models one PRD per domain at a time. In a real team, two developers might have concurrent PRDs in the billing domain — both minting rule IDs from the same domain-rules.yaml. validate-knowledge would catch conflicts between their rules, but the process for coordinating concurrent PRDs (who goes first, how do they coordinate AGENT_CONTEXT.md updates) is undefined. | G    | **P1**   |
| 26  | process        | **No brownfield onboarding path**                        | The framework assumes a greenfield project. For an existing codebase with existing business rules, existing architecture, and existing test suites, there is no skill for "read all this code and create AGENT_CONTEXT.md and domain-rules.yaml from what already exists." `/initialize-knowledge-loop` sets up scaffolding but doesn't extract existing knowledge.                        | G    | **P1**   |
| 27  | seam contracts | **Enforcement is aspirational**                          | CONTRACT.md says "Edit only via /define-seam-contract — never manually" and "Both domain owners must approve any change." These are comments. Nothing technically enforces them. An agent can edit CONTRACT.md directly. A PR can merge without the other domain owner reviewing. The contract relies on humans reading the comment and obeying it.                                        | W    | **P1**   |
| 28  | process        | **Cross-domain features require manual coordination**    | If a feature spans billing and loyalty, you need grill-me in both domains, update-agent-context in both, and coordinated ticket planning. The framework has per-domain skills but no "feature spanning N domains" skill. The developer must manually sequence the domain-specific steps and ensure consistency between them.                                                               | G    | **P2**   |

## Testing

| #   | Area | Issue                                                               | Description                                                                                                                                                                                                                                                                                                                                                           | Type | Severity |
| --- | ---- | ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---- | -------- |
| 29  | tdd  | **"Observable behavior" vs implementation detail — no enforcement** | The TDD skill says "public interface only · describes observable outcome." But agents frequently write tests that check internal state, call private methods through test utilities, or assert on implementation details. There is no linter, no review checklist, and no gate that validates a test is testing behavior rather than implementation.                  | W    | **P1**   |
| 30  | tdd  | **Contract tests have no re-run trigger**                           | Contract tests are written at seam establishment. If the contract changes (new field added, payload type changes), the consumer's contract tests should re-run automatically. The framework has no mechanism to detect "contract changed → trigger consumer tests." A contract change that breaks a consumer is silent until the consumer runs their full test suite. | G    | **P2**   |

## Framework-Level

| #   | Area               | Issue                                             | Description                                                                                                                                                                                                                                                                                                                                                                                                                              | Type | Severity |
| --- | ------------------ | ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---- | -------- |
| 31  | process            | **Claude/gh CLI lock-in**                         | The entire framework requires Claude Code, the `gh` CLI, and GitHub issues for PRDs. Teams using other AI tools (Cursor, Copilot, Gemini), other VCS (GitLab, BitBucket), or other issue trackers (Jira, Linear) cannot use this framework without significant adaptation. There is no abstraction layer.                                                                                                                                | W    | **P1**   |
| 32  | process            | **No time or size guidelines**                    | The framework is all process, no scale. How long should grill-me take? How many tickets should a PRD produce (max/min)? How many rules should a domain have before it needs splitting? How long is "too long" for a single ticket? Without these guidelines, teams have no way to detect when they're doing the process badly.                                                                                                           | G    | **P2**   |
| 33  | overhauls          | **Batch supersede has no coordination primitive** | A major overhaul superseding 8 rules triggers 8 independent validate-knowledge runs, each potentially raising its own CHAIN-IMPACT gate. These decisions are all part of one intentional product call but the framework treats them as 8 independent conflicts. There is no "coordinated batch" primitive that says "I know I'm replacing all of these simultaneously — check internal consistency, not each one against the old state." | G    | **P1**   |
| 34  | validate-knowledge | **6 outcomes may not cover emerging patterns**    | CLEAN, DECLARED-WRITE, INFERRED-WRITE, SCOPE-INFERRED, CHAIN-IMPACT, CONFLICT-UNRESOLVABLE. Real codebases produce edge cases: a rule that partially overlaps two existing rules (neither fully supersedes either), a rule that is domain-correct but violates a cross-cutting policy, a rule that is correct now but would conflict with a planned (not yet PRD'd) rule. None of these have an outcome.                                 | W    | **P2**   |
| 35  | process            | **Claude window context limits mid-ticket**       | Each ticket is one Claude window. If the ticket is large — many tests, many files, extensive refactoring — the window can approach context limits mid-session. There is no recovery procedure: no "pick up where you left off" skill, no handoff mechanism within a ticket. The developer has to start a new window and manually re-establish the state.                                                                                 | W    | **P1**   |
