1
PRD must be manually promoted from Draft → Submitted
Fix
▶
Issue

No gate between a PRD being written and tickets starting. An agent could begin building before the human reviewed and approved.

Fix

Added a "Promote PRD: Draft → Submitted" button at the bottom of the FEATURE phase. Tickets cannot begin until the human manually clicks it.

What it means

PRD is locked at submission — no further edits without a new PRD. Claude never promotes automatically. Human owns the gate.

Upload documents during grill-me
New
▶
Issue

Background docs (specs, legacy system docs, competitor analysis) were ignored. Grill-me would ask questions the docs already answered.

Fix

Added "Before starting — read any uploaded docs" as the first step of /grill-me. Agent reads all uploaded files before asking any questions.

What it means

Grill-me treats uploaded docs as pre-loaded context. The 5-branch interview focuses only on genuine gaps — not re-asking what's already written.

Save grill-me results in a persistent log
New
▶
Issue

Grill-me output lived only in the conversation. Future sessions, humans, and Claude couldn't search past decisions or re-used questions.

Fix

Final step of /grill-me saves the session to grill-me-docs/<prd-name>/grill-me-NN.md. Append-only. Never overwritten. Session number increments on each re-run.

Supersede vs scope branch — three distinct paths modelled
Design
▶
Issue

When a new feature applied to only a subset (e.g. VIP customers), it was unclear whether that supersedes the original general rule or just branches from it.

Fix

Three explicit outcomes now modelled in validate-knowledge and the flowchart:

What it means

Supersede is not the only path. The framework models the full shape of the change rather than forcing every partial overlap into a supersede.

5
Tests on scope splits and compositions
Design
▶
Issue

For scope splits and compositions, it was unclear which existing tests were still valid, which needed updating, and who was responsible.

Fix

Handled at the /tdd level. The rule action (supersede / SCOPE-INFERRED / composition) is stated in the PRD; each ticket reads the PRD and writes tests for its scope while preserving existing tests for unchanged scopes.

What it means

No test management lives in domain-rules.yaml. The PRD is the authority on what changed. The test file is the authority on whether the code matches.

Ticket dependencies + cross-window handoffs
New
▶
Issue

Each ticket runs in its own Claude window with no memory of prior tickets. If Ticket 2 called a function created by Ticket 1, the Ticket 2 window had no way to know that interface existed.

Fix (two parts)

/break-into-tickets marks each checkbox with an explicit dependency: | requires: Ticket 1 merged.

## Ticket handoffs section added to AGENT_CONTEXT.md — each ticket appends a brief note before opening its PR. Cleared at ship-feature.

What it means

Tickets can run in separate windows without losing continuity. The handoff section is the lightweight shared memory between sequential tickets in the same PRD.

Removed test_cases field from domain-rules.yaml
Fix
▶
Issue

test_cases in YAML duplicated what test files already proved. Had no enforcement mechanism, added maintenance overhead, and was fragile — a rule description change required updating both YAML and tests.

Fix

Removed test_cases field entirely from the schema. Also removed spec-alignment CI job that was checking YAML strings against test file strings — a string-vs-string check, not behaviour-vs-code.

What it means

Test files are the sole authority for test lifecycle. YAML owns the business rule definition. The two don't duplicate each other.

AGENT_CONTEXT.md — archetype-based templates
Design
▶
Issue

The single fixed AGENT_CONTEXT.md template was too rigid. Backend domains need owned tables; AI agent domains need escalation logic; cross-cutting domains need neither. One template became a graveyard of N/A sections.

Fix

/scaffold-domain now asks which archetype, then generates a matching template. New sections can be added freely when grill-me surfaces content with no existing home.

What it means

The template is a starting point, not a constraint. Archetype determines defaults; the domain's actual needs determine what gets added or dropped.

10
No draft rules in domain-rules.yaml (Option C)
Design
▶
Issue

Rules were written into YAML with status: draft as soon as they were discovered in grill-me — before any code existed. This polluted the "what is live" view. Draft rules and live rules were indistinguishable at a glance.

Fix

Rules stay plain English in AGENT_CONTEXT.md until they ship. YAML never receives a draft. The only write to domain-rules.yaml is at /ship-feature, directly as status: active.

What it means

domain-rules.yaml only ever contains rules with shipped code behind them. No draft status exists anywhere in the YAML schema.

11
Rule ID format — PRD-number-based (Option 1)
Design
▶
Issue

The old RULE-DOMAIN-NNN format used a counter. Two PRDs written before either shipped could mint the same counter value — a collision. The counter also wasn't available during grill-me.

Fix

New format: RULE-<DOMAIN>-P<issue-number>-<seq>
e.g. RULE-BILLING-P10-1

IDs minted in /write-a-prd immediately after gh issue create returns the issue number.

What it means

Collision-proof — GitHub issue numbers are globally unique. IDs are stable from PRD creation through shipping. No shared counter needed. No registry.

Skills extracted to individual .md files + config
Infra
▶
Issue

All 20 skills lived as JavaScript strings in skill-content.js. Not executable by Claude. Git diffs for any skill change mixed with unrelated changes. No per-skill git history.

Fix

Each skill extracted to .claude/commands/<skill-name>.md. Claude Code picks these up as slash commands automatically. HTML viewer now fetches .md files directly — no more skill-content.js dependency.

What it means

Skills are versioned independently. Every skill edit has its own git blame. The HTML viewer and the executable command are always the same file.

Major overhauls — gaps identified (not yet built)
Gap
▶
Question raised

How does the framework handle a big-bang refactor — ripping out an entire subsystem with a better idea? How do docs and YAML catch up?

What works today

Pure architectural refactor (same rules, different code) works fine. 2–3 rule replacements via the supersede path work cleanly.

Proposed (not built)

/overhaul-domain skill with an overhaul manifest, single validate-knowledge scan across the whole batch, and section-level AGENT_CONTEXT.md rewrites.

GapWhy it breaks
Batch supersede — 8 rules8 independent validate-knowledge runs, each can raise its own CHAIN-IMPACT gate. No "treat as one coordinated batch" primitive.
AGENT_CONTEXT.md resetship-feature uses Edit tool for targeted updates. Wholesale section rewrites require rewriting every line — no section-level replace supported.
Refactor PRD templateThe PRD template is additive. No "Motivation: why current approach is wrong" section. No "what is being removed" section.
Multi-domain overhaulsMerging or splitting domains touches CLAUDE.md, multiple AGENT_CONTEXT.md files, and moves rules between domains. No skill covers this coordination.
Stale AGENT_CONTEXT.md referencesAfter a refactor, module names and file paths in AGENT_CONTEXT.md may reference things that were deleted. No audit mechanism.
