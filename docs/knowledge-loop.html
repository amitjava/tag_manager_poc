3 — The git parallel — conservative over optimistic

Git resolves merges structurally: same lines changed differently → conflict. It does not reason. It does not fetch context. If there is any structural ambiguity, it halts. The conservative principle is absolute.

Our system does more than git: it reads semantic content and fetches context. This creates a temptation toward optimism — "we can reason to a resolution, so let's auto-execute." The exercise showed this is dangerous. The more we added "smart" auto-resolve paths, the more we introduced silent LLM failure risk.

The rule we landed on: if the resolution involves LLM reasoning about content, involve a human. LLM reasoning is fallible. A wrong silent write is worse than an unnecessary confirmation prompt. The three human outcomes all involve reasoning about meaning, not structure.

What this approach maps to in industry

Conventional Commits + Protected Branch Rules (GitHub/GitLab) The pattern of declaring intent clearly in a human-authored message so that automation can execute it without ambiguity is widespread in CI/CD — Conventional Commits (feat:, fix:, breaking change:) are exactly this. GitHub branch protection rules enforce that certain changes require explicit human review before merge — the same conservative gate we apply to SCOPE-INFERRED and CHAIN-IMPACT.
ADR (Architecture Decision Records) — Michael Nygard, 2011 The original ADR format (Context → Decision → Consequences → Status) is the closest industry parallel to our domain-rules.yaml. Each ADR has a status (proposed → accepted → superseded → deprecated), an explicit supersedes pointer, and a rationale. Our YAML adds machine-readability and CI linkage — the structural difference is that ADRs are prose documents while our rules are schema-validated and testable.
Database Migration Versioning — Flyway / Liquibase The immutable-history model (never delete, only add new migration versions) is identical to our supersede/retire model. Flyway uses sequential version numbers to track schema state; we use rule IDs. Both systems maintain a full audit trail and forbid retroactive rewriting of committed versions. The key difference: migrations are code, ours are business rules — but the versioning discipline is the same.
Feature Flags with Audit Trails — LaunchDarkly / Split.io These systems enforce that any change to a flag's targeting rules is attributed (who, when, why), versioned, and reviewable. Our modified_prd / modified_by fields mirror this — any retroactive change to an existing rule (like the scope annotation in PRD #5) must carry attribution. Without it, the system becomes unauditable over time.
IETF RFC Process — Status field evolution RFCs have a formal status lifecycle: Proposed Standard → Draft Standard → Internet Standard, and can be Obsoleted by a successor RFC with an explicit Obsoletes: header. This is conceptually identical to our active → superseded → retired lifecycle with superseded_by pointers. The industry learned that technical standards need immutable history and explicit succession chains — we apply the same discipline to business rules.

4 — Why YAML-first — the structured source of truth

The alternative is storing business rules as English prose in DOMAIN_BUSINESS.md. Here is why that fails at scale:

  • Conflict detection becomes semantic search. To know if a new rule conflicts, you must read all existing rules and judge by meaning. At 50 rules, this works. At 200, it is unreliable — LLMs produce false negatives (miss conflicts) and false positives (flag non-conflicts).
  • No machine-readable identity. Prose rules have no stable ID. "Customers earn 1 point per dollar" in PRD #1 and "earn rate is 1× for Bronze" in PRD #2 might refer to the same rule. The YAML caches verbose plain_english for each rule — a cheap LLM can scan 20 rules in one pass and judge overlap by text. Without the cache, you would re-read all previous PRDs to understand what rules exist — O(n) token growth as history scales.
  • No CI linkage. You cannot run a test against an English sentence. YAML rules carry test_cases — CI verifies rules against actual code on every build. If the code and the rule ever diverge, the build breaks.
  • No schema enforcement. Prose cannot enforce "every active rule must have a test case" or "plain_english must be verbose enough for LLM text matching." Schema validation catches structural hallucinations before commit.

DOMAIN_BUSINESS.md still exists — it is the human-readable layer, generated from the YAML. But it is a view, not the source. The YAML is the source.

6 — Key learnings from this design exercise

Clear PRD prose is the linchpin

Everything in the DECLARED-WRITE path depends on the PM writing clear intent in the PRD narrative — "this replaces the current earn rate", "this adds a modifier on top of", "this feature is being removed". No rule IDs, no structured annotation required. validate-knowledge reads that prose and determines whether it is unambiguous enough to execute without fetching the historical PRD. The PM's job is not to know rule IDs — it is to state intent clearly. That clarity, written at decision time, is the highest-leverage design choice in the whole system.

The why field is what enables conflict detection

Two formulas — floor(order_total / 100) and floor(order_total / 100) × tier_mult — look like a conflict. The why field on 1.1.1 ("simple flat rate, no tier") makes clear it is a supersede, not a contradiction. Without the why field, validate-knowledge cannot distinguish intentional replacement from accidental duplication. Verbose rules are not overhead — they are what makes the system work.

Modification attribution is not optional

Any time validate-knowledge modifies an existing rule (not just creates one), it must record modified_prd and modified_by: validate-knowledge in the YAML. Without this, git blame on domain-rules.yaml cannot explain why 1.1.3's scope changed between PRD #3 and PRD #5. Attribution makes the audit trail complete. Any auto-modification without attribution is a silent write.

Conservative is safer than optimistic — always

Every time we added a "smart" auto-resolve path in this design session, we found a failure mode. SCOPE-INFERRED auto-resolve: silently modifies another author's rule. CHAIN-IMPACT auto-resolve: depends on LLM formula reading, which can be wrong. The more sophisticated the reasoning, the more ways it can fail silently. The cost of an unnecessary human prompt is low. The cost of a wrong silent write is high. Default to human.

Immutable history is not optional

Rules are never deleted — only superseded or retired. This was a structural choice, not a cosmetic one. If validate-knowledge ever writes a wrong rule, the worst case is a wrong active rule — visible in the YAML, fixable by marking it superseded and writing the correct version. With deletion, the worst case is permanent data loss. Immutable history is what makes the system recoverable from LLM mistakes.

CI test cases close the loop

domain-rules.yaml carries test_cases for every active rule. A CI check reads the YAML and verifies test cases pass against the actual code. If validate-knowledge writes a rule with a wrong formula, or if code is deployed that contradicts an active rule, the build fails. The code is the final validator — not the LLM, not the human review, not the schema. Test cases are what give the YAML teeth.

The human gate is at PRD writing time for declared changes

For DECLARED-WRITE, the PM already made the decision when they wrote the Business Rules Affected block. validate-knowledge is not a second review — it is execution. Adding a human confirmation step on top of an already-declared intent would be redundant and would slow down the pipeline for no safety gain. The design insight: push the human gate as early as possible (to PRD writing), and make it structural (a required field), not optional (a prompt the PM might skim).

plain_english string Required Primary matching surface for conflict detection. Must be verbose — 3+ sentences covering: what the rule governs, when it applies, what it does not apply to, edge cases, and business intent. A cheap LLM compares this field against all other active rules to detect overlap. Short values like "1 point per dollar" are invalid — the LLM cannot reliably distinguish two short descriptions. Minimum ~80 words.
formula string Required if active The calculation or condition in plain notation. Examples: floor(net_total_cents / 100) * tier_mult, min(redeem_points, floor(gross * 0.4)). Must match what the code implements — CI verifies this via test_cases. Omitted for retired rules.
why string Required Business rationale — why this rule exists or why this version supersedes the previous. Enables validate-knowledge to distinguish intentional replacement from accidental duplication. Without why, two rules with similar formulas look like a conflict even when one clearly replaces the other.
PROVENANCE
introduced_prd integer Required PRD number that first introduced this rule. Used by validate-knowledge to fetch the historical PRD when chain analysis needs context. Also the primary audit trail link — every rule traces back to a product decision.
user_story_ref string Optional Which user stories in the PRD this rule satisfies. Example: "PRD #3 Story 1, Story 2". Useful for tracing a rule back to a specific acceptance criterion but not required for conflict detection or CI.
modified_prd integer Set by validate-knowledge PRD that caused a retroactive modification to this rule (e.g. scope annotation added by SCOPE-INFERRED). Without this, git blame on domain-rules.yaml cannot explain why a rule changed between PRDs. Never set manually.
modified_by string Set by validate-knowledge Attribution for retroactive modifications. Always "validate-knowledge". Distinguishes automated modifications from original author intent. Required alongside modified_prd whenever a rule is changed after initial creation.
SUPERSEDE LINEAGE
supersedes string Conditional ID of the rule this rule replaces. Required when this rule is a newer version of an existing rule. validate-knowledge uses this to mark the referenced rule as superseded and sets its superseded_by field. If present, the referenced rule must exist and be active or draft.
superseded_by string Set by validate-knowledge ID of the rule that replaced this one. Set automatically when a rule's status changes to superseded. Never written manually. Present on all superseded rules, absent on all other statuses.
COMPOSITION (two rules active simultaneously on same concept)
composes_with string Conditional ID of the rule this rule combines with. Both rules remain active simultaneously — this one modifies or extends the other. Triggers validate-knowledge-COMPOSITION outcome instead of conflict. Requires composition_order and modifier_type to be set.
composition_order enum Required if composes_with set applied_before or applied_after. Defines evaluation order — which rule runs first. Example: base earn rule runs first, weekend modifier applies after. Absence when composes_with is set is a schema validation error.
modifier_type enum Required if composes_with set How this rule modifies the base rule's result. One of: additive (adds to result), multiplicative (multiplies result), conditional (replaces result under specific condition). Used to generate the combined formula shown in the validate-knowledge COMPOSITION output.
SCOPE (non-overlapping customer segments)
scope string Optional Named customer segment this rule applies to. Examples: vip, non_vip, bronze. Absence means the rule applies to all customers. When an incoming rule has a narrower scope than an existing rule on the same concept, validate-knowledge triggers SCOPE-INFERRED rather than conflict — the two rules cover non-overlapping populations.
scope_condition string Required if scope set Boolean expression that evaluates the scope at runtime. Example: "customer.vip == true". Must be a deterministic condition against available customer attributes. Absence when scope is set is a schema validation error.
DEPENDENCY
depends_on array Optional Array of rule IDs whose output this rule's formula consumes. Example: [1.4.1] means this rule receives a pre-computed value from rule 1.4.1. When any rule in this array is superseded or retired, validate-knowledge triggers CHAIN-IMPACT and halts for human confirmation before writing.
RETIREMENT
retired_prd integer Required if retired PRD number that retired this rule. Required when status: retired. Serves the same audit purpose as introduced_prd — every lifecycle event traces to a product decision.
retire_reason string Required if retired Why the rule was retired. Should include business context — e.g. "Birthday bonus removed — 0.3% redemption rate, high ops cost." Enables future teams to understand whether a feature was retired for good reasons or could be revived.
CI VERIFICATION
test_cases array Required if active Array of {input, expected} pairs. A CI check reads every active rule and verifies each test case passes against the actual code. This is the strongest safeguard: if validate-knowledge writes a rule with a wrong formula, or if code is deployed that contradicts an active rule, the CI build fails. Removed from CI when a rule is retired (test_cases: []). At least one case required per active rule.

The knowledge hierarchy — reading order for agents

When an agent starts any task, it reads files in this order. Each layer provides context for the next:

  1. CLAUDE.md — process rules and phase definitions (always first)
  2. AGENT_CONTEXT.md (platform) — reading order and active cross-domain contracts
  3. PLATFORM_CONTEXT.md — what capabilities exist and which are live
  4. backend/src/domains/<name>/docs/AGENT_CONTEXT.md — domain-specific entry point
  5. DOMAIN_BUSINESS.md — use cases + use-case→rule-ID reference table (links into YAML)
  6. domain-rules.yaml — active rules with full formulas and IDs (authoritative source of truth)
  7. Any cross-domain contracts relevant to the task (docs/cross-domain/) — if applicable

DOMAIN_BUSINESS.md and domain-rules.yaml work together: the business doc provides context and maps use cases to rule IDs; the YAML provides the authoritative formula, test cases, and lineage. Neither alone is sufficient — an agent needs both.
