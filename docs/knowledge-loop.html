The Knowledge Loop

8 scenarios showing every way a rule can move through the loop — create, update, cross-domain, retire, near-miss, human approval, draft collision, and revert. Each PRD shows the exact state of domain-rules.yaml and DOMAIN_BUSINESS.md before and after.

The Loop every feature follows this path

Phase 1
/grill-me
Extract rules, actors, edge cases. Draft rules written to YAML with status: draft, introduced_prd: TBD.
Phase 4
/write-a-prd
PRD opened as GitHub issue. introduced_prd written back to YAML immediately. No more TBD.
Phase 6
/tdd
RED tests first, then GREEN. Every rule must have passing tests before it can be promoted.
Ship
/ship-feature
Rules promoted to active. Docs regenerated from YAML. Platform context updated. Loop closed.
🔒
/validate-knowledge — runs before every write to any knowledge doc Conflict key = entity + field + operation. If two rules share the same key → CONFLICT, halt, show diff. Human approves or rejects. If different key → CLEAN, proceed. Cross-domain dep scan runs on every supersede. Human is the semantic validator — not the LLM.

All 8 Scenarios at a Glance

🆕
Create

New rule, no existing coverage. Gate: CLEAN. Draft → active on ship.

✏️
Update

Same conflict key. Gate: CONFLICT. Human approves supersede. Old rule kept as history.

🔗
Cross-Domain

New key, different domain. Gate: CLEAN + dep notice. depends_on field tracked.

🗑
Retire

Feature removed. Rule status → retired. Never deleted. Dep scan first.

👀
Near-Miss

Different key → CLEAN, but semantic interaction noticed. Human informed, confirms acceptable.

🛑
Conflict→Rejected

True conflict. Gate halts. Human reviews diff. Rejects. YAML unchanged. Trail in closed PRD.

💥
Draft Collision

Two drafts, same key. Gate catches on merge. Engineers align. One rule ships.

↩
Revert

New rule replaces old one with original intent. Old IDs preserved. Full lineage maintained.

After 8 PRDs, a new Claude reading DOMAIN_BUSINESS.md sees exactly 3 active rules — no contradictions, no stale entries, no guessing.


The YAML is the single source of truth. The doc is generated from it. The gate is deterministic. Human judgment is required for exactly one thing: reading the diff and saying yes or no. Everything else — conflict detection, dep scanning, promotion gating, doc regeneration — is automated.


The LLM's job on PRD #100 is identical to PRD #1: look up the rule by ID, apply the declared change, show the diff. No inference about what other rules mean. No guessing what's current. The structure does the heavy lifting.

service/loyalty.service.ts Written by Claude during /tdd
Inline
Rule IDs appear as inline code comments next to the line that implements them.

// Best-effort: order never blocked by points failure (RULE-004)

This is convention, not enforcement. The comment helps a future developer understand why a line exists. When a rule is superseded, the developer updates the comment ID — the gate does not check this automatically.
router/loyalty.router.ts Written by Claude during /tdd
Inline
Same convention as the service — rule IDs cited in comments where the router enforces a rule directly (e.g. error code mapping, cap enforcement). Not every line needs a rule ID, only lines where the behaviour would be confusing without the reference.
repository/loyalty.repository.ts Written by Claude during /tdd
None
Pure data access — Prisma queries, no business logic. Rule IDs do not belong here. If you see a rule ID in a repository file, that's a smell that business logic leaked into the data layer.
📁 backend/src/domains/loyalty/ (test files) test suite — the only automated enforcement layer
File
Rule IDs?
What it contains + example
loyalty.service.unit.test.ts Written by Claude during /tdd
Inline
Rule IDs appear in describe() blocks to name which rule the test group covers.

describe("earn stamps (RULE-001, RULE-002)", () => { ... })

This is the strongest link in the chain — a failing test here means the code contradicts the rule. This is the CI enforcement layer. When RULE-001 is superseded, its test cases stop running (status: superseded → excluded from CI). The new rule's tests take over.
loyalty.router.integration.test.ts Written by Claude during /tdd
Inline
Same convention — describe blocks name the rule being tested end-to-end. These run against a real test database so they verify the full stack, not just the service layer in isolation.
