VIP gross earning — scoped variant, not a conflict
VIP customers should earn on gross total (pre-discount), not effective total. This hits customer.loyaltyPoints.earn again. In this case it does — so it auto-resolves without a human.

Methodology — validate-knowledge reference guide
How the system decides what to auto-execute and when to involve a human. All outcome codes, the YAML-first rationale, PRD fallback strategy, token cost model, industry parallels, and key learnings from this design exercise.

1 — When does validate-knowledge involve a human?

The decision is not about confidence. It is about who has authority to make the change. Three questions, in order:

Incoming rule arrives with a conflict_key ↓ Q1: Is there an existing active rule on the same conflict_key? ├── NO → validate-knowledge-CLEAN → auto-write. Done. └── YES → continue ↓ Q2: Did the incoming PRD explicitly declare rule_id + action in Business Rules Affected? ├── YES → validate-knowledge-DECLARED-WRITE → auto-execute declared intent. Done. └── NO → fetch PRDs for context → semantic comparison ├── intent unambiguous → validate-knowledge-INFERRED-WRITE → auto. Done. └── continue ↓ Q3: What kind of conflict is it? ├── Scope inferred on a rule we did not author → validate-knowledge-SCOPE-INFERRED → ❌ HUMAN │ Human authorises annotation on someone else's rule. ├── Dependency chain affected by change → validate-knowledge-CHAIN-IMPACT → ❌ HUMAN │ Human confirms LLM formula scan is correct. └── Contradictory product intent, no resolution path → validate-knowledge-CONFLICT-UNRESOLVABLE → ❌ HUMAN Human makes product decision. No write until resolved.

The key insight: the human gate for DECLARED-WRITE cases is at PRD writing time, not at validate-knowledge time. When the PM writes action: supersede RULE-EARN-001 in Business Rules Affected, that is the human decision. validate-knowledge is executing an already-authorised instruction.

3 — The git parallel — conservative over optimistic

Git resolves merges structurally: same lines changed differently → conflict. It does not reason. It does not fetch context. If there is any structural ambiguity, it halts. The conservative principle is absolute.

Our system does more than git: it reads semantic content and fetches context. This creates a temptation toward optimism — "we can reason to a resolution, so let's auto-execute." The exercise showed this is dangerous. The more we added "smart" auto-resolve paths, the more we introduced silent LLM failure risk.

The rule we landed on: if the resolution involves LLM reasoning about content, involve a human. LLM reasoning is fallible. A wrong silent write is worse than an unnecessary confirmation prompt. The three human outcomes all involve reasoning about meaning, not structure.

What this approach maps to in industry

Conventional Commits + Protected Branch Rules (GitHub/GitLab) The pattern of declaring intent in a structured commit message (equivalent to our Business Rules Affected block) so that automation can execute it deterministically is widespread in CI/CD. GitHub branch protection rules enforce that certain changes require explicit human review before merge — the same conservative gate we apply to SCOPE-INFERRED and CHAIN-IMPACT.
ADR (Architecture Decision Records) — Michael Nygard, 2011 The original ADR format (Context → Decision → Consequences → Status) is the closest industry parallel to our domain-rules.yaml. Each ADR has a status (proposed → accepted → superseded → deprecated), an explicit supersedes pointer, and a rationale. Our YAML adds machine-readability and CI linkage — the structural difference is that ADRs are prose documents while our rules are schema-validated and testable.
Database Migration Versioning — Flyway / Liquibase The immutable-history model (never delete, only add new migration versions) is identical to our supersede/retire model. Flyway uses sequential version numbers to track schema state; we use rule IDs. Both systems maintain a full audit trail and forbid retroactive rewriting of committed versions. The key difference: migrations are code, ours are business rules — but the versioning discipline is the same.
Feature Flags with Audit Trails — LaunchDarkly / Split.io These systems enforce that any change to a flag's targeting rules is attributed (who, when, why), versioned, and reviewable. Our modified_prd / modified_by fields mirror this — any retroactive change to an existing rule (like the scope annotation in PRD #5) must carry attribution. Without it, the system becomes unauditable over time.
IETF RFC Process — Status field evolution RFCs have a formal status lifecycle: Proposed Standard → Draft Standard → Internet Standard, and can be Obsoleted by a successor RFC with an explicit Obsoletes: header. This is conceptually identical to our active → superseded → retired lifecycle with superseded_by pointers. The industry learned that technical standards need immutable history and explicit succession chains — we apply the same discipline to business rules.

4 — Why YAML-first — the structured source of truth

The alternative is storing business rules as English prose in DOMAIN_BUSINESS.md. Here is why that fails at scale:

  • Conflict detection becomes semantic search. To know if a new rule conflicts, you must read all existing rules and judge by meaning. At 50 rules, this works. At 200, it is unreliable — LLMs produce false negatives (miss conflicts) and false positives (flag non-conflicts).
  • No machine-readable identity. Prose rules have no stable ID. "Customers earn 1 point per dollar" in PRD #1 and "earn rate is 1× for Bronze" in PRD #2 might refer to the same rule. A lookup by conflict_key is O(1) and deterministic. A lookup by prose is O(n) and probabilistic.
  • No CI linkage. You cannot run a test against an English sentence. YAML rules carry test_cases — CI verifies rules against actual code on every build. If the code and the rule ever diverge, the build breaks.
  • No schema enforcement. Prose cannot enforce "every active rule must have a test case" or "exactly one active rule per conflict_key (except composition/scoped variants)." Schema validation catches structural hallucinations before commit.

DOMAIN_BUSINESS.md still exists — it is the human-readable layer, generated from the YAML. But it is a view, not the source. The YAML is the source.

5 — The PRD fallback — when and why we fetch, and what it costs

The YAML is the fast path. PRD fetches are the fallback. validate-knowledge only fetches a PRD when the YAML lookup alone cannot determine the outcome.

Path
~tokens
CLEAN — read YAML only
~400
DECLARED-WRITE — read YAML only
~500
INFERRED-WRITE — YAML + 2 PRD fetches
~6,000
SCOPE-INFERRED / CHAIN-IMPACT — YAML + 2–3 PRDs
~10,000
CONFLICT-UNRESOLVABLE — YAML + 3+ PRDs + conflict map
~20,000

The critical property: most PRDs are DECLARED-WRITE or CLEAN. They cost ~500 tokens. PRD fetches only happen when the conflict detection fires — which is rare for a well-maintained rule set. Without the YAML fast path, every PRD would need to read all previous PRDs to check for conflicts — O(n²) token growth as the system scales. With the YAML, conflict detection is O(1).

At 200 PRDs shipped: without YAML, PRD #200 would need to scan ~199 previous PRDs. With YAML, PRD #200 reads one file regardless of history length.

6 — Key learnings from this design exercise

The rule_id in the PRD is the linchpin

Everything in the DECLARED-WRITE path depends on the PM writing action: supersede RULE-EARN-001 in Business Rules Affected. Without that declaration, validate-knowledge falls back to PRD fetch + semantic comparison. The rule ID forces the human to be explicit at decision time — not at review time. This is the highest-leverage design choice in the whole system.

The why field is what enables conflict detection

Two formulas — floor(order_total / 100) and floor(order_total / 100) × tier_mult — look like a conflict. The why field on RULE-EARN-001 ("simple flat rate, no tier") makes clear it is a supersede, not a contradiction. Without the why field, validate-knowledge cannot distinguish intentional replacement from accidental duplication. Verbose rules are not overhead — they are what makes the system work.

Modification attribution is not optional

Any time validate-knowledge modifies an existing rule (not just creates one), it must record modified_prd and modified_by: validate-knowledge in the YAML. Without this, git blame on domain-rules.yaml cannot explain why RULE-EARN-003's scope changed between PRD #3 and PRD #5. Attribution makes the audit trail complete. Any auto-modification without attribution is a silent write.

Conservative is safer than optimistic — always

Every time we added a "smart" auto-resolve path in this design session, we found a failure mode. SCOPE-INFERRED auto-resolve: silently modifies another author's rule. CHAIN-IMPACT auto-resolve: depends on LLM formula reading, which can be wrong. The more sophisticated the reasoning, the more ways it can fail silently. The cost of an unnecessary human prompt is low. The cost of a wrong silent write is high. Default to human.

Immutable history is not optional

Rules are never deleted — only superseded or retired. This was a structural choice, not a cosmetic one. If validate-knowledge ever writes a wrong rule, the worst case is a wrong active rule — visible in the YAML, fixable by marking it superseded and writing the correct version. With deletion, the worst case is permanent data loss. Immutable history is what makes the system recoverable from LLM mistakes.

CI test cases close the loop

domain-rules.yaml carries test_cases for every active rule. A CI check reads the YAML and verifies test cases pass against the actual code. If validate-knowledge writes a rule with a wrong formula, or if code is deployed that contradicts an active rule, the build fails. The code is the final validator — not the LLM, not the human review, not the schema. Test cases are what give the YAML teeth.

The human gate is at PRD writing time for declared changes

For DECLARED-WRITE, the PM already made the decision when they wrote the Business Rules Affected block. validate-knowledge is not a second review — it is execution. Adding a human confirmation step on top of an already-declared intent would be redundant and would slow down the pipeline for no safety gain. The design insight: push the human gate as early as possible (to PRD writing), and make it structural (a required field), not optional (a prompt the PM might skim).
