What We Set Out to Do

We already had a working 7-phase AI engineering process — grill-me, write-a-prd, prd-to-plan, tdd, triage-issue — proven on the Tag Manager build. The process produced clean, tested code. But it had a gap: after each feature shipped, the knowledge layer was empty.

The gap discovered: After the catalog domain was built with 21 passing tests, the domain had zero knowledge docs. No DOMAIN_BUSINESS.md, no DOMAIN_API.md, no DOMAIN_DATA.md, no openapi.yaml, no AGENT_CONTEXT.md. The code was right. The knowledge layer was missing. The next Claude session would have no context to work from.

The fix was not to write docs manually. It was to define where in the pipeline each gap occurred and build a skill to close it automatically at that exact transition point.

Before orders could call catalog, a 3-document contract was established: what business capability is consumed, how it is integrated (in-process service call), and exactly which fields cross the boundary with their source-of-truth and snapshot rules. The contract exists before the code, not after.

The Knowledge Consistency Problem

Writing docs once is easy. Keeping them consistent across 200+ PRDs over time is the real problem — because an LLM both reads and writes the docs. PRD 30 adds a billing rule. PRD 100 changes it. If both survive in DOMAIN_BUSINESS.md, every session after the conflict gets wrong information. The error is silent and compounds.

Five industry patterns were evaluated: ADR, database migrations, event sourcing, knowledge graphs, and structured YAML with ID matching. The chosen approach borrows from all five.

The four-layer quality architecture

Layer 1
Structure
Business rules live in domain-rules.yaml with IDs, entity+field+operation conflict key, and status. Conflict detection is a deterministic lookup — no LLM semantic matching.
Layer 2
Surgical edit
Skills always read before writing. Changes target specific rule IDs. Edit tool only — never overwrite the whole file. Nothing is deleted; superseded rules stay in history.
Layer 3
Human approval gate
/validate-knowledge shows the exact diff before any write. Human reads raw diff and approves. The human is the semantic validator — not the LLM.
Layer 4
CI validation
Every active rule has test cases in domain-rules.yaml. CI validates test cases against actual code. If rule says X but code does Y → CI fails → blocked from merge.

Conflict test result: We simulated PRD #30 (price > $100 → premium badge) then PRD #100 (price > $50 → premium badge). The gate blocked PRD #100 with a side-by-side conflict map, forced human resolution, and correctly applied the supersede. After both PRDs: exactly one active rule, one superseded rule with full lineage. Zero contradictions.

/scaffold-domain Project start — once per domain All domain stub docs: AGENT_CONTEXT.md, DOMAIN_BUSINESS.md, DOMAIN_API.md, DOMAIN_BACKEND_ARCHITECTURE.md, DOMAIN_DATA.md, openapi.yaml, domain-rules.yaml (backend + frontend)

/validate-knowledge Before any knowledge doc write APPROVED (with diff for human review) or BLOCKED (conflict map + resolution options). Never writes without human confirmation.
/generate-domain-docs Phase 6 → Phase 7 transition Reads actual code → DOMAIN_DATA.md (from schema), openapi.yaml (from router), DOMAIN_API.md (human-readable), DOMAIN_BACKEND_ARCHITECTURE.md (module map, data flows, patterns, debt).
/ship-feature After Phase 7 QA passes PROCESS_LOG step, draft rules → active with test cases, PLATFORM_CONTEXT.md capabilities updated, FEATURES.md indexed, reverse sync to business docs, git commit.
/define-seam-contract Phase 0 — cross-domain features only Interviews user (10 questions). Writes docs/contracts/<provider>→<consumer>/: FUNCTIONAL.md, ARCHITECTURE.md, DATA.md. Updates platform context.
